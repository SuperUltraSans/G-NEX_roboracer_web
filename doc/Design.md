# RoboRacer 대회 홈페이지 — 프론트엔드 디자인 지시서

- 작성일: 2026-10-12
- 대상: 이 저장소를 구현하는 코딩 에이전트
- 관계: `INSTRUCTIONS.md`와 함께 읽는다. 시각 디자인(색, 서체, 레이아웃, 모션, 히어로)에 관해서는 이 문서가 우선한다.

---

## 0. 이 문서가 필요한 이유

"예쁘게", "모던하고 깔끔하게" 같은 지시만 받으면 모델은 통계적으로 가장 흔한 선택으로 수렴하고, 그 결과가 흔히 말하는 "AI가 만든 템플릿" 느낌이 된다. 이 문서는 그런 기본값으로 돌아갈 여지를 줄이기 위한 브리프, 제약, 절차를 정한다.

원칙 한 줄: 대담함은 한 곳(첫 화면 히어로)에만 쓰고, 나머지는 차분하고 절제한다.

---

## 1. 브리프

| 항목 | 내용 |
|---|---|
| 주제 | 학교 주최 RoboRacer(구 F1TENTH) 대회. 1/10 스케일 자율주행 차량이 실내 트랙에서 겨루는 레이스 |
| 사용자 | 참가 학생 팀, 관람객(학내외), 운영진·심판 |
| 사이트의 주된 일 | 1) 대회를 알리고 신청(구글 폼)으로 보낸다 2) 대회 당일 예선 기록과 본선 대진을 실시간으로 보여준다 |
| 사용자가 고정한 방향 | 첫 화면 히어로는 남색·어두운 파랑과 네온 빛. 본문은 흰 바탕에 어두운 글씨 |
| 레퍼런스 세계 | 불 꺼진 실내 트랙, 자율주행 차가 LiDAR로 보는 세계(스캔 링, 주행 궤적), 모터스포츠 계측(타이밍 타워, 피트월 모니터) |
| 아닌 것 | 사이버펑크 도시, 게임 UI, SaaS 랜딩 페이지 |

네온은 분위기용 장식이 아니라 이 세계 안의 의미를 가진다. 시안은 센서가 보는 것(스캔, 실시간 데이터), 주황은 차가 갈 길과 지금 주목할 것이다. 이 연결을 끊고 네온을 아무 데나 쓰면 곧바로 흔한 "사이버" 템플릿이 된다.

화면은 두 종류의 면으로 나뉜다. 어두운 면(히어로, 헤더, 푸터)은 밤의 트랙이고, 밝은 면(본문)은 정보를 읽는 곳이다. 어두운 히어로에서 흰 본문으로 넘어가는 순간 자체가 구조이므로, 두 면을 섞지 않고 경계를 의도적으로 설계한다(6.4).

## 2. 진행 절차 (이 순서를 지킨다)

### Step A — 방향 시안 3개 제안 후 사용자 선택 대기

각 시안에 다음을 포함해서 `docs/DESIGN_DIRECTIONS.md`에 작성한다.

1. 이름과 한 줄 콘셉트
2. 색: 3장의 제약 안에서 이름 붙인 hex 4~6개
3. 서체: 역할(표시, 본문, 기록 숫자)별 서체와 고른 이유, 한글 지원 여부
4. 레이아웃: 히어로와 소개 섹션 첫 화면의 ASCII 와이어프레임, 정렬 방식(좌측, 비대칭 등)
5. 원칙 3개, 그리고 "대담함을 쓸 한 곳"이 무엇인지
6. 페이지 로드 시 단 한 번의 연출(6.6) 구상
7. 남색 히어로에서 흰 본문으로 넘어가는 전환 방식(6.4)

시안의 출발점 예시. 더 나은 해석이 있으면 바꿔도 된다.

- 계측: 타이밍 타워와 피트월 모니터. 숫자가 주인공이고 정보 밀도가 높다.
- 야간 레이스 포스터: 큰 타이포, 대담한 크롭, 비대칭 편집. 히어로 이미지의 장면이 중심이다.
- 센서 시점: LiDAR 스캔 링, 좌표 눈금, 궤적 선 같은 얇은 선 그래픽이 구조 장치가 된다.

작성 후 각 시안을 4장의 금지 목록과 대조한다. 비슷한 다른 대회 사이트를 만들어도 똑같이 나올 것 같은 부분이 있으면 고치고, 무엇을 왜 바꿨는지 적는다.

그다음 사용자에게 선택을 요청하고, 선택 전에는 UI 스타일 구현을 시작하지 않는다. 백엔드와 데이터 계층 같은 기능 구현은 병행해도 된다.

### Step B — 토큰 확정

선택된 방향으로 `frontend/src/styles/tokens.css`를 확정하고, 결정 내용을 `docs/DECISIONS.md`에 기록한다.

### Step C — 구현과 자기 점검

구현하면서 8장의 스크린샷 점검 루프를 최소 2회 돈다.

Claude Code 환경에 frontend-design 스킬이나 플러그인이 설치되어 있으면 Step A 전에 읽는다. 없으면 이 문서만으로 진행한다.

## 3. 색

### 3.1 초기 토큰

히어로 이미지를 같은 색 값으로 주문했으므로, 이미지와 사이트의 색이 맞도록 아래 값에서 출발한다. Step A에서 시안별로 조정할 수 있지만 역할과 의미는 유지한다.

네온 원색(`#3FE0FF`, `#FF6A1A`)은 흰 바탕에서 대비가 크게 부족하다(각각 약 1.6:1, 2.9:1). 그래서 시안과 주황은 면마다 다른 값을 쓴다.

어두운 면 (히어로, 헤더, 푸터):

| 이름 | 변수 | 값 | 역할 | 대비 |
|---|---|---|---|---|
| 심야 남색 | `--ink-950` | `#071028` | 헤더, 푸터 배경 | |
| 트랙 남색 | `--ink-900` | `#0B1A3F` | 히어로 하단 페이드의 목표색 | |
| 덕트 블루 | `--ink-700` | `#1C3A7A` | 어두운 면 경계선 | |
| 밤 글자 | `--on-dark` | `#E8EEFF` | 어두운 면 텍스트 | 16.3:1 |
| 밤 보조 글자 | `--on-dark-dim` | `#93A7CF` | 어두운 면 보조 텍스트 | 7.0:1 |
| 스캔 시안 | `--neon` | `#3FE0FF` | 어두운 면의 실시간 표시, 포커스 링 | 10.8:1 |
| 신호 주황 | `--signal` | `#FF6A1A` | 어두운 면 CTA 채움 (글자는 `--ink-900`, 5.9:1) | |
| 오류(밤) | `--danger-on-dark` | `#FF5A6E` | 어두운 면 오류 표시 | 5.6:1 |

밝은 면 (본문):

| 이름 | 변수 | 값 | 역할 | 흰색 대비 |
|---|---|---|---|---|
| 종이 | `--paper` | `#FFFFFF` | 본문 배경 | |
| 보조 면 | `--paper-2` | `#F2F5FB` | 표 머리글, 패널, 목차 | |
| 구분선 | `--line` | `#D5DDEC` | 장식용 구분선 | |
| 입력 테두리 | `--line-strong` | `#7A88A6` | 입력 필드, 체크박스 테두리 | 3.6:1 |
| 본문 글자 | `--ink-text` | `#0B1A3F` | 본문 텍스트 (검정 대신 남색) | 17.0:1 |
| 보조 글자 | `--ink-text-dim` | `#4A5878` | 보조 텍스트 | 7.1:1 |
| 시안(낮) | `--neon-ink` | `#007A99` | 밝은 면의 실시간 표시, 포커스 링 | 4.9:1 |
| 시안 틴트 | `--neon-tint` | `#E0F8FF` | 방금 갱신된 행의 배경 (글자는 `--ink-text`) | |
| 주황(낮) | `--signal-ink` | `#C24A00` | 밝은 면 CTA 채움(흰 글씨), 1위·진행 중 강조 | 4.9:1 |
| 오류 | `--danger` | `#C8102E` | 오류, 실격. 문구와 함께 표시 | 5.9:1 |

대비 수치는 WCAG 공식으로 계산한 값이다. 값을 바꾸면 다시 계산한다.

### 3.2 규칙

- 어두운 면은 눈에 보이게 "파랑"이어야 한다. `#0B0B0B`, `#111` 같은 거의 검정색으로 바꾸지 않는다.
- 밝은 면은 흰색과 차가운 보조 면으로 구성한다. 크림·베이지 같은 따뜻한 바탕(`#F4F1EA` 류)으로 바꾸지 않는다.
- 밝은 면에서 `--neon`, `--signal` 원색을 글자, 테두리, 아이콘 색으로 쓰지 않는다. 반드시 `--neon-ink`, `--signal-ink`를 쓴다.
- 시안은 실시간·센서 데이터를 뜻할 때만 쓴다. 장식용 테두리나 제목 색으로 쓰지 않는다.
- 주황은 한 화면에서 2~3곳 이하로 쓴다. 사용자가 할 행동이나 지금 주목할 대상에만 쓴다.
- 발광 효과(`box-shadow`, `text-shadow` glow)는 어두운 면에서만, 히어로의 한 요소 정도로 제한한다. 흰 바탕에서는 발광 효과를 쓰지 않는다.
- 그라데이션은 기능적인 두 곳에만 쓴다. 히어로 텍스트 가독성을 위한 스크림, 그리고 히어로 하단을 `--ink-900`으로 마무리하는 페이드다. 남색과 흰색을 그라데이션으로 섞지 않는다(중간에 탁한 회청색 띠가 생긴다).
- 본문 대비는 WCAG AA(4.5:1) 이상, 입력 필드 테두리 같은 UI 요소는 3:1 이상이어야 한다.

## 4. 금지 목록

### 4.1 흔한 AI 템플릿 패턴

- 보라~파랑, 보라~분홍 그라데이션, 메시 그라데이션 배경
- Inter, Roboto, Arial, Helvetica, `system-ui` 같은 기본 서체를 그대로 쓰기. 자주 쓰이는 Poppins, Montserrat, Space Grotesk도 이유 없이 쓰지 않는다.
- 이모지 아이콘
- 가운데 정렬 히어로 → 3열 기능 카드 → CTA 띠가 반복되는 구조
- 모든 블록을 같은 반경의 둥근 카드로 자르고 같은 회색 그림자를 깔기
- 글래스모피즘(반투명 배경 + `backdrop-filter: blur`)
- 모든 섹션에 같은 여백 주기
- 섹션마다 fade-up 진입 효과, 모든 카드에 hover 효과
- 제목에서 한 단어만 다른 색, 이탤릭, 굵기로 강조하기
- 모든 제목 위에 자간을 벌린 대문자 소제목(eyebrow) 달기, 라벨을 전부 대문자로 쓰기
- `A · B · C`처럼 가운뎃점으로 이은 메타 문자열, 버튼·링크 끝에 붙이는 `→`
- 작은 라벨마다 모노스페이스 쓰기
- 실제로 순서가 아닌 내용에 `01 / 02 / 03` 번호 붙이기
- 신문처럼 촘촘한 단, 머리카락 선, 모서리 0의 조합. 이것도 흔한 기본값이므로 선택한 방향이 정당화할 때만 쓴다.

### 4.2 이 브리프 특유의 함정 (남색 + 네온)

- 글리치 텍스트, 화면 전체 스캔라인·노이즈 오버레이, 홀로그램 효과, HUD 모서리 꺾쇠 장식
- Orbitron, Audiowide 같은 "SF 테크" 서체
- 모든 테두리와 텍스트에 네온 발광 넣기
- 의미 없는 숫자 스트림이나 가짜 데이터 장식

## 5. 타이포그래피

- 역할은 표시(대형 제목), 본문, 기록 숫자 세 가지다. 패밀리는 1~2개로 하고, 2개라면 확실히 구분되게 한다.
- 한국어 모드에서 보이는 모든 텍스트는 한글 글리프가 있는 서체로 렌더링되어야 한다. 표시 서체가 라틴 전용이면 한글 짝 서체를 명시하고, 한·영 두 모드 모두 스크린샷으로 확인한다.
- 본문 한글에 Pretendard나 Noto Sans KR 같은 흔한 선택을 쓸 수는 있다. 그 경우 개성은 표시 서체와 타입 스케일에서 나와야 하고, 선택 이유를 `docs/DECISIONS.md`에 적는다.
- 기록 숫자(랩타임, 격차, 순위)는 `font-variant-numeric: tabular-nums`를 지원하는 서체로 쓰고 반드시 적용한다. 모노스페이스는 기록 표 안에서만 허용하고, 장식용 라벨에는 쓰지 않는다.
- 히어로 제목과 본문의 크기 대비를 크게 잡고 `clamp()`로 유동 크기를 쓴다. 한글 본문 행간은 1.6~1.8, 줄 길이는 80자 미만, 규칙 페이지 본문은 65~75자로 한다.
- 제목 타이포 자체를 디자인 요소로 쓴다. 단, 4.1의 한 단어 강조는 하지 않는다.
- 한글 웹폰트는 용량이 크다. Google Fonts의 unicode-range 분할을 쓰거나 서브셋을 만들고, `font-display: swap`을 적용하며, 실제로 쓰는 굵기만 불러온다.
- 서체 후보는 Step A에서 이유와 함께 제시한다. 존재 여부, 한글 지원, 라이선스(OFL 등)를 직접 확인한다.

## 6. 첫 화면 히어로 (소개 페이지 상단)

첫 진입 시 화면 전체를 배경 이미지 한 장이 채우고, 아래로 스크롤하면 끊김 없이 소개 섹션으로 이어진다. 이 사이트에서 대담함을 쓰는 한 곳이다. 배경 영상은 쓰지 않는다.

### 6.1 자산

```
frontend/
├── assets-src/hero/
│   ├── hero-source.png          # 생성된 원본 (가로형)
│   └── hero-mobile-source.png   # 선택. 세로형 원본
└── public/hero/                 # 빌드 스크립트가 생성 (6.8)
    ├── hero-{폭}.avif / .webp / .jpg
    ├── hero-mobile-{폭}.avif / .webp / .jpg   # 세로 원본이 있을 때만
    └── manifest.json
```

- 원본 이미지는 사용자가 생성해서 넣는다. 장면: 불 꺼진 실내 트랙, 화면 오른쪽에 LiDAR를 단 1/10 차량, 시안 스캔 링, 주황 궤적 선. 왼쪽 절반은 어둡게 비워 두고, 하단은 `#0B1A3F`로 페이드된다.
- 생성 도구의 출력 비율이 16:9가 아닐 수 있다(예: 3:2). 화면 비율 차이는 `object-fit: cover` 크롭으로 처리하고, 원본을 억지로 늘리거나 비율을 바꾸지 않는다.
- 자산이 아직 없으면 작업을 멈추지 않는다. `--ink-900` 단색 위에 차분한 플레이스홀더(예: 얇은 시안 원호 하나)를 두고 진행한다. 이 플레이스홀더는 자산이 들어오면 제거한다.

### 6.2 마크업과 동작

- `<picture>` 안에 avif, webp 순으로 `<source>`를 두고, jpg `<img>`를 기본으로 둔다. 모두 `srcset`과 `sizes="100vw"`를 쓴다. `srcset`은 `manifest.json`을 기준으로 만든다.
- 세로 원본이 있으면 `media="(max-width: 767px) and (orientation: portrait)"`인 `<source>`를 앞에 추가한다. 없으면 `object-position`을 조정해 좁은 화면에서도 차가 보이게 한다.
- 히어로 이미지는 LCP 요소다. `<img>`에 `fetchpriority="high"`를 주고 `loading="lazy"`를 쓰지 않는다.
- 장식용 이미지이므로 `alt=""`로 둔다. 대회 정보는 텍스트로 전달한다.
- 이미지는 `object-fit: cover`로 채우고, 히어로 높이는 `100svh`로 한다.
- 이미지 위에 좌→우 방향의 어두운 스크림을 둬서 왼쪽 텍스트의 가독성을 확보한다.
- 이미지를 천천히 확대·이동시키는 반복 효과(Ken Burns)는 쓰지 않는다.

### 6.3 레이아웃

- 텍스트는 왼쪽 정렬로 그리드의 왼쪽 5~6열에 둔다. 피사체(차)는 오른쪽에 있으므로 겹치지 않는다.
- 들어갈 내용: 대회명, 일시, 장소(모두 `TBD:`), 버튼 두 개. "신청하기"는 `--signal` 채움에 `--ink-900` 글자, "실시간 기록 보기"는 `--on-dark` 외곽선이다.
- 일시와 장소를 가운뎃점으로 이어 한 줄에 몰아넣지 않는다. 각각 독립된 정보로 배치한다.

### 6.4 히어로에서 흰 본문으로의 전환

- 히어로는 하단이 `--ink-900` 단색으로 깔끔하게 끝나야 한다. 이미지 자체의 페이드가 부족할 수 있으므로, 히어로 하단 25~30%에 투명 → `--ink-900` CSS 그라데이션을 덧씌워 보정한다.
- 그 아래에서 흰 소개 섹션이 시작된다. 남색에서 흰색으로 넘어가는 그라데이션은 쓰지 않는다.
- 전환 방식은 Step A에서 시안별로 하나를 제안한다. 후보는 다음과 같고, 더 나은 방식이 있으면 바꿔도 된다.
  1. 깔끔한 경계: 남색과 흰색이 한 직선으로 맞닿는다. 스크롤 유도 선이 그 경계에 걸친다.
  2. 궤적 선 연결: 히어로의 스크롤 유도 선이 경계를 넘어 흰 본문까지 이어지고, 소개 섹션의 진행 방식(예선 → 본선) 흐름선이 된다. 선 색은 면에 맞는 토큰으로 바뀐다.
  3. 겹침: 흰 소개 섹션의 첫 블록이 히어로 하단 위로 일부 겹쳐 올라온다.
- 1440px, 768px, 390px 폭의 스크린샷에서 경계가 의도한 모양으로 보이고, 탁한 중간색 띠나 1px 틈이 없어야 한다.

### 6.5 스크롤

- 스크롤 하이재킹이나 강제 스냅은 쓰지 않는다. 사용자가 스크롤하는 만큼만 움직인다.
- 스크롤 진행에 따라 히어로 텍스트가 살짝 위로 이동하며 옅어진다. `transform`과 `opacity`만 쓰고, 모션 감소 설정 시 끈다.
- 헤더는 히어로 위에서 투명하고, 히어로를 지나면 `--ink-950` 배경이 생긴다. IntersectionObserver로 처리한다. 히어로가 없는 페이지(일정, 규칙, 신청, 모니터링, 관리자)는 처음부터 `--ink-950` 헤더를 쓴다. 헤더와 푸터는 어두운 면이고, 그 사이 본문은 밝은 면이다.
- 히어로 하단에 스크롤 유도 표시를 둔다. 텍스트 없는 얇은 세로선이 적당하고, `aria-label`은 i18n으로 넣는다. 클릭하면 `#intro`로 이동하고, 모션 감소 설정 시에는 즉시 이동한다.

### 6.6 단 한 번의 로드 연출

- 페이지 로드 시 한 번만 재생하는 연출을 하나 둔다. 예: 시안 스캔 선이 좌→우로 한 번 지나가며 제목을 드러낸다. 1.2초 이내로 끝낸다.
- 구체적인 연출은 Step A에서 시안별로 제안한다.
- 이 연출 외에 사용자 행동 없이 저절로 움직이는 효과는 라이브 표시 점의 맥동과 실시간 갱신 하이라이트뿐이다.

### 6.7 성능 예산

- 1920px 폭 기준으로 avif는 가급적 250KB 이하, jpg는 400KB 이하로 한다.
- 예산을 넘으면 품질 값을 조금씩 낮추되, 6.8의 밴딩 점검을 통과해야 한다.

### 6.8 이미지 빌드 스크립트

`frontend/scripts/build-hero.mjs`를 만들고 `npm run build:hero`로 실행한다. `sharp`를 devDependency로 쓴다.

- 입력: `assets-src/hero/hero-source.png`, 있으면 `hero-mobile-source.png`도 처리한다.
- 출력 폭: 가로형 2560, 1920, 1280, 828 / 세로형 1080, 750
- 출력 형식: avif, webp, jpg(mozjpeg)
- 원본 폭보다 큰 크기는 만들지 않는다(`withoutEnlargement`). 원본이 1920px보다 좁으면 그 사실을 출력하고, 업스케일 여부는 사용자에게 확인한 뒤 `docs/DECISIONS.md`에 기록한다.
- 시작 품질 값은 avif 50, webp 75, jpg 78로 하고, 스크립트 상단 상수로 둔다.
- 밴딩 점검: 어두운 남색 그라데이션과 안개는 압축하면 계단 모양 띠(밴딩)가 생기기 쉽다. 각 형식의 1920px 결과를 원본과 나란히 확대해서 보고, 밴딩이 보이면 해당 형식의 품질 값을 올린다. 결과는 `docs/DECISIONS.md`에 적는다.
- 스크립트는 생성한 파일 목록과 용량을 출력하고, 실제 생성된 폭·형식·경로를 `public/hero/manifest.json`에 쓴다.

## 7. 페이지별 가이드

각 페이지에서 "정보가 하는 일"이 구조를 정한다. 장식은 그다음이다.

- 소개 섹션
  - 진행 방식(예선 → 본선)은 실제 순서이므로 순서를 드러내는 표현을 써도 된다.
  - 3열 카드 대신 트랙이나 주행 궤적처럼 이 브리프에서 나온 장치를 고려한다.
  - 주최·후원 로고 자리는 조용하게 둔다.
- 일정
  - 시간이 구조다. 시간축을 따라 배치한다.
  - 현재 또는 다음 일정만 신호 주황으로 강조하고, 지난 일정은 대비를 낮춘다.
- 규칙
  - 읽기가 우선이다. 장식을 최소화하고 목차와 문단 간격에 집중한다.
  - 흰 바탕에 `--ink-text` 본문을 쓴다. 목차와 표 머리글은 `--paper-2`로 구분한다.
- 신청
  - 접수 상태(준비 중, 접수 예정, 접수 중, 마감)가 첫눈에 보여야 한다.
  - 버튼 문구는 일어날 행동을 그대로 말한다. 예: "구글 폼에서 신청하기".
- 모니터링
  - 숫자가 주인공이다. 순위와 랩타임을 크게 쓰고 tabular 숫자를 적용한다.
  - 1위와 진행 중인 매치는 `--signal-ink`, 방금 갱신된 행은 `--neon-tint` 배경(1.5초)으로 표시한다.
  - 라이브 표시 점(`--neon-ink`)의 느린 맥동은 허용된 반복 애니메이션이다. 연결이 끊기면 그 사실을 분명히 보여준다.
  - 대진표는 라운드를 열로 두고, 진출 관계가 보이게 한다.
  - 선택(P2): 현장 프로젝터용 큰 글씨 모드(`/live?display=1`). 헤더와 내비를 숨기고 리더보드와 대진만 크게 보여준다. 어두운 행사장에서는 흰 화면이 눈부실 수 있으므로, 이 모드에 한해 어두운 면 토큰(남색 바탕, `--neon`, `--signal`)을 쓴다.
- 관리자
  - 장식 없이 밝은 면 토큰을 쓴다.
  - 심판이 휴대폰으로 쓰므로 터치 타깃은 44px 이상, 입력 필드는 크게 만든다.

### 7.1 문구

- 문구도 디자인이다. 화면에 필요한 말만 쓰고, 사용자가 이해하는 말로 쓴다.
- 버튼은 행동을 말한다. 같은 행동은 처음부터 끝까지 같은 이름을 쓴다. 예: "저장" 버튼을 누르면 "저장됨"이 표시된다.
- 빈 상태는 다음에 할 일을 안내한다. 오류는 무엇이 잘못됐고 어떻게 고치는지 말하며, 사과하지 않는다.
- 대회 고유 정보는 지어내지 않고 `TBD:`로 둔다. UI 문구(버튼, 빈 상태, 오류, 연결 상태)는 한·영 모두 직접 작성한다.

## 8. 스크린샷 자기 점검 루프

- 도구: Playwright MCP가 연결되어 있으면 그것을 쓴다. 없으면 `@playwright/test`로 `npm run shots` 스크립트를 만든다.
- 캡처 대상: 소개(히어로 + 스크롤 후), 일정, 규칙, 신청, 모니터링(mock 모드), 관리자 기록 입력
- 캡처 크기: 1440×900, 768×1024, 390×844. 각 크기마다 ko와 en 두 모드를 찍는다.
- 저장 위치: `design-review/<라운드>/`. 이 폴더는 `.gitignore`에 넣는다.

각 라운드마다 스크린샷을 직접 보고 `docs/DESIGN_REVIEW.md`에 기록한다.

1. 템플릿처럼 보이는 부분 3개와 그 수정 방법
2. 4장 금지 목록 위반 여부
3. 남색 히어로에서 흰 본문으로의 전환 (탁한 띠, 틈, 어색한 단차)
4. 한·영 전환 시 줄바꿈, 넘침, 서체 깨짐
5. 대비, 포커스 표시, 390px에서의 가로 넘침
6. 이번 라운드에서 뺀 장식 하나 (외출 전 거울 앞에서 액세서리 하나를 빼듯이)

수정 전후 스크린샷을 함께 남기고, 최소 2라운드를 진행한다.

## 9. 품질 하한

- 360px 폭까지 반응형. 대진표 영역 안의 가로 스크롤만 허용한다.
- 키보드 포커스 표시: 밝은 면은 `--neon-ink`, 어두운 면은 `--neon` 2px outline과 offset. 포커스 표시를 지우지 않는다.
- 모션 감소 설정 존중: 로드 연출, 스크롤 연출, 하이라이트 애니메이션, 라이브 점 맥동 모두 대상이다.
- 대비 AA, 색만으로 정보를 전달하지 않기(상태에는 문구나 모양을 함께 쓴다)
- 장식용 이미지는 `aria-hidden`, 의미 있는 이미지는 alt를 단다. `<html lang>`을 언어에 맞게 바꾼다.
- 아이콘은 한 세트(외곽선형, 같은 선 두께)만 쓴다. 숫자나 문구로 충분하면 아이콘을 빼는 쪽을 택한다.
